# GitHub Actions secrets for scheduled ingestion

Add these secrets to the repository before triggering the workflows.

**Where to add them:** GitHub repo → Settings → Secrets and variables → Actions → New repository secret

## Required secrets

- `DATABASE_URL` — Supabase Session pooler connection string
- `SPOTIFY_CLIENT_ID` — from Spotify Developer Dashboard
- `SPOTIFY_CLIENT_SECRET` — from Spotify Developer Dashboard
- `SPOTIFY_REFRESH_TOKEN` — generated by running `uv run python scripts/spotify_auth.py` locally (expires, see below)
- `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` — Web Push (see below). Since v0.89 every notification the crons send (digests, badges, snapshots, alerts) is a push; there is no mail and no Gmail secret any more. `GMAIL_USER`, `GMAIL_APP_PASSWORD` and `EMAIL_RECIPIENT` can be deleted.
- `TOKEN_ENC_KEY` — (v0.81) the **same** value as the Rotor hub's Vercel env var. Lets the crons decrypt the cron token Rotor stores in `hub_oauth_tokens` (option A, below). Optional: without it the crons use `SPOTIFY_REFRESH_TOKEN` exactly as before.

The values are the same as in your local `.env` file — copy them over. The last.fm secrets are no longer used by any workflow (the last.fm cron was retired in v0.38).

## Testing the workflow

Don't use "Run workflow" on **Scheduled ingest** for a quick check: every job in that file also runs on a manual dispatch, so it fires the weekly playlist rewrite, the snapshots and the monthly refreshes all at once. To check the Spotify credentials, run **Ingest freshness monitor** instead (Actions tab → Ingest freshness monitor → Run workflow → main). It makes one recently-played call and compares it with the DB.

## Cron token from Rotor (option A, v0.81)

`lib/spotify.py` first looks for a `cron` row in `hub_oauth_tokens` (migration 0019), decrypts it with `TOKEN_ENC_KEY`, and refreshes with `SPOTIFY_CLIENT_ID` / `SPOTIFY_CLIENT_SECRET`. It falls back to `SPOTIFY_REFRESH_TOKEN` when the key is unset, the row is missing, the row was minted for another Spotify app, or Spotify refuses it (`invalid_grant`; written to the row so Rotor shows it). A rotated refresh token is stored back; the authorization date never moves.

Mint the row from Rotor: **Settings › Connections › Connect crons** (needs `SPOTIFY_CRON_CLIENT_ID` / `SPOTIFY_CRON_CLIENT_SECRET` in Vercel = the cron app's ID and secret, and `https://<rotor>.vercel.app/auth/callback` in the cron app's redirect URIs). After that, every 6 months is one Reconnect tap instead of the manual steps below. The scope set is the same as `scripts/spotify_auth.py`.

## Rotor jobs (v0.81, v0.82)

| Job | Schedule | What |
|---|---|---|
| `sync-playlist-mirror` | `15 4 * * *` | `scripts/sync_playlist_mirror.py`: `/me/playlists` → `spotify_playlists`; items for unmanaged playlists, snapshots, custom and Missed new tracks when their `snapshot_id` changed. Read-only towards Spotify. |
| `generate-daily-picks` | `30 4 * * *` | `scripts/generate_daily_picks.py`: 5 candidates for today (Europe/Amsterdam). DB only. Skips a day that already has candidates. |
| `hub-jobs.yml` (job) | dispatch, input `job_id` | (v0.82) Runs one queued `hub_jobs` row: `reseed_daily_pick` ("Shuffle the deck"), `refresh_managed` (Refresh now / Rebuild for one Auto playlist), `push_test`. Started by the hub with `GITHUB_DISPATCH_TOKEN`. |
| `hub-jobs.yml` (daily) | `47 5 * * *` | (v0.82) `scripts/run_hub_job.py --daily`: sweeps stale jobs, rebuilds snapshots with a pending Rebuild, generates today's pick if missing and sends the "daily pick ready" notification, token-expiry notifications (14 and 3 days left, or dead), rules catalog export. |

`daily-pick-reseed.yml` (v0.81) is gone: "Shuffle the deck" is a `reseed_daily_pick` job since v0.82.

Manual runs: `uv run python scripts/generate_daily_picks.py --dry-run` prints today's deck without writing. `uv run python scripts/update_managed_playlists.py --only <playlist_id>` refreshes one Auto playlist (refuses anything without a managed suffix).

## Rotor stats rollups (v0.83)

`scripts/ingest_spotify_recent.py` ends with `SELECT hub.refresh_rollups()` (`lib/rollups.py`,
migration 0023). It recomputes only the days touched by the plays just ingested (~2 s at 440k
plays) and rebuilds everything once every 24 h (~11 s). The timings are printed in the ingest
log (`[rollups] refreshed in … ms`). It never fails the ingest; before 0023 is applied it is a
no-op. A full rebuild by hand: `SELECT hub.refresh_rollups(true);`

## Elsewhere refresh (v0.84)

The daily `hub-jobs.yml` run also refreshes YouTube / SoundCloud metadata (`lib/collections_refresh.py`,
also `uv run python scripts/refresh_collections.py`): playlists synced > 25 days ago are re-read,
other videos re-checked, and YouTube data that can't be refreshed within 30 days is deleted
(YouTube API Services policy III.E.4). Needs the GitHub secret `YOUTUBE_API_KEY` (same key as the
hub's Vercel env). Without it, imports are disabled and old YouTube data is deleted after 30 days.

## Rotor job runner and notifications (v0.82)

Extra secrets for `hub-jobs.yml` (the other Spotify/DB secrets are the ones above):

- `VAPID_PRIVATE_KEY` — Web Push signing key. Generate once with `uv run python scripts/generate_vapid_keys.py`; the matching `VAPID_PUBLIC_KEY` goes into the hub's Vercel env. Without it jobs still run, only notifications are skipped.
- `VAPID_SUBJECT` — contact for push services: your Rotor URL (`https://<rotor>.vercel.app`) or a `mailto:` address.

The hub needs `GITHUB_DISPATCH_TOKEN` (Vercel env): a fine-grained PAT for this repository only, permission **Actions: Read and write**. It is used for one call, `POST /repos/{repo}/actions/workflows/hub-jobs.yml/dispatches`. Without it the hub still works; Refresh now / Rebuild are disabled and Shuffle the deck starts the current deck over.

A job is `queued` → `running` → `done` / `failed`. Queued jobs older than 15 minutes and running jobs older than 30 minutes are marked failed. Retry re-runs the same row, up to 3 attempts.

## Spotify refresh token: re-mint every 6 months

Since July 2026 Spotify refresh tokens stop working **6 months after the authorization that created them**. Refreshing access tokens does not extend that. When the token expires, every Spotify call fails with `invalid_grant` and all crons that touch Spotify go red.

Re-mint before the date in the log below:

1. `uv run python scripts/spotify_auth.py` — a browser opens; approve the Spotify dialog. The script always does a fresh authorization and prints the new token plus its expiry date.
2. GitHub: Settings → Secrets and variables → Actions → `SPOTIFY_REFRESH_TOKEN` → Update (or `gh secret set SPOTIFY_REFRESH_TOKEN` and paste the value when prompted).
3. Streamlit Cloud: the app → Settings → Secrets → `SPOTIFY_REFRESH_TOKEN`.
4. Local `.env`: replace `SPOTIFY_REFRESH_TOKEN=`.
5. Run **Ingest freshness monitor** manually and check it goes green.
6. Add a row to the log below.

Scopes are fixed at minting time. If you add a scope to `SPOTIFY_SCOPES` in `scripts/spotify_auth.py`, re-mint, or the new feature gets `403 Insufficient client scope` (the crons themselves keep running: `lib/spotify.py` deliberately doesn't check scopes).

|---|---|---|
| 2026-05-21 | 2026-11-21 | Inferred from the last scope change (`user-follow-read`, v0.36); token without `user-library-modify` |
| 2026-11-03 | 2027-05-04 | Re-minted in v0.80.1; adds `user-library-modify` |

## Keepalive (60-day inactivity rule)

GitHub disables a public repository's scheduled workflows after 60 days without repository activity. `.github/workflows/keepalive.yml` runs every Monday and re-enables `scheduled-ingest.yml`, `ingest-monitor.yml`, `hub-jobs.yml` (v0.82) and itself through the REST API, then fails the run if any of them is not `active`. Merging any PR into `main` also resets the timer.

Check the state any time:

```bash
gh api repos/steynvg00/music-tracker/actions/workflows --jq '.workflows[] | [.path, .state] | @tsv'
```

A workflow in state `disabled_inactivity` can be switched back on with `gh workflow enable <file>.yml` or the Actions tab → workflow → Enable workflow. Plays missed while the crons were off are only recoverable for the last 50 tracks (`/me/player/recently-played`).
